# 사회복지사·요양보호사 역할과 반복 요청 검토

## 역할

| 역할 | 담당 기능 |
|---|---|
| 어르신 | 도움 요청, 지역·희망 일정 신청, 자신의 일정 확인·진행 전 취소 |
| 사회복지사 | 요청 분류 검토, 요양보호사 배정, 일정 제안·변경·취소, 수행 기록 확인, 통계, 반복 요청 상담·후속 계획 |
| 요양보호사 | 가능한 지역·시간 등록, 일정 수락·거절, 확정된 일정의 직접 돌봄 시작·완료, 수행 불가·특이사항 보고 |
| 관리자 | 계정 승인·감사 기록. 사회복지사나 요양보호사의 수행 권한을 자동으로 겸하지 않음 |

앱 메뉴뿐 아니라 API에서 역할과 담당자를 확인합니다. 요양보호사는 제안별 수락·거절 API로 결정합니다. 기존 booking decision API는 어르신의 취소만 지원합니다. [3단계 일정 안내](SCHEDULING.md)를 참고하세요.

## 사회복지사 작업 순서

1. **새 요청**에서 요청을 담당합니다.
2. **요청 검토**에서 원문과 분류를 확인하고 위험도를 확정합니다. 검토하지 않은 요청은 배정할 수 없습니다.
3. 같은 화면의 **2·3차 일정 제안**에서 이용자가 등록한 지역과 일치하는 근무 가능 시간을 확인합니다.
4. 이용자의 필요한 시간을 확인한 뒤 제안합니다. 요양보호사가 앱에서 수락해야 확정됩니다. 이것은 앱 밖에서 확인했다는 기록이며 실제 연락을 자동 발송하지 않습니다.
5. **일정 관리**에서 어르신이 직접 신청한 일정도 관리 담당을 맡고 수락을 요청할 수 있습니다. 다른 사회복지사가 맡은 일정을 임의로 변경할 수 없습니다.
6. 배정 후 담당 요양보호사·날짜·시간을 다른 가능한 슬롯으로 변경할 수 있습니다. 동일 지역 후보를 먼저 표시하고, 서버는 양측의 등록 지역과 중복 시간을 다시 검증합니다. 변경 전 슬롯은 마감합니다.
7. 요양보호사가 남긴 수행 기록을 확인합니다. 수행 불가·특이사항은 ‘사회복지사 확인 필요’로 표시되어 연락·후속 계획이 필요합니다. 이 표시는 자동으로 해제되지 않습니다.

기존 돌봄 원문 전체는 요양보호사에게 공개하지 않습니다. 요양보호사는 배정된 이용자 ID·지역·시간·도움 종류를 확인합니다. 상세 방문 장소·구체적 현장 지시는 기관의 확인 절차로 전달해야 합니다.

## 요양보호사 작업 순서

- **근무 가능 시간**: 활동 지역과 시간을 직접 등록합니다. 이 화면에서 실제 방문 일정을 확정하지 않습니다.
- **돌봄 수행**: 제안된 일정을 수락하거나 사유를 남겨 거절합니다. 긴급 일정도 수락이 필요합니다.
- 방문 당일 **돌봄 시작** → 수행 내용을 적고 **돌봄 완료**를 남깁니다. 시작 전 완료 처리는 허용하지 않습니다.
- 수행이 어렵거나 특이사항이 있으면 내용을 기록해 사회복지사가 확인하도록 합니다. 같은 건을 두 번 완료 처리하지 않습니다.
- 다른 요양보호사의 일정 수행, 요청 위험도 변경, 사회복지사 통계 조회는 허용하지 않습니다.

기존에 확정된 일정은 유지합니다. 관리 담당이 없는 기존 일정은 사회복지사가 ‘이 일정 관리 맡기’를 선택한 뒤 기록 확인·조율할 수 있습니다.

## 통계 기준

사회복지사의 **현황**에서 최근 7일·30일·90일을 선택합니다.

- 전체 요청 수와 식사·이동·집안일·말벗·복약·기타별 건수.
- 각 종류 안에서 긴급 확인·도움 필요·일반 확인·담당자 확인 분류별 건수.
- 분류 검토 대기/완료와 사회복지사 담당 미배정/배정 건수.
- 같은 기간 신청된 일정의 조율 대기·확정·진행·완료·특이사항·취소 건수.

요청과 일정은 각각 **접수 시각부터 최근 N일** 기준이며, 목록의 100건 제한과 무관하게 전체를 집계합니다. 위험도는 현재 값입니다. 분류 검토 완료는 실제 돌봄 완료와 다릅니다. 방문일 기준 실적 통계가 아닙니다. 이 버전은 단일 기관 운영 전제이며 여러 기관 데이터를 한 DB에 넣어 분리 운영하는 기능은 없습니다.

## 반복 요청에서 자동화와 사람의 개입

기준은 **동일 어르신 + 동일 도움 종류 + 최근 7일에 3회 이상**입니다. 글이 완전히 같다는 뜻이나 동일 원인이 입증됐다는 뜻은 아닙니다. LLM이 임의로 판단하지 않는 규칙이며 자동 묶음 이후 사회복지사가 원문을 확인합니다.

| 자동 처리 | 사람이 결정 |
|---|---|
| 새 접수 시 횟수 계산, 반복 검토 건 생성 | 묶음 담당, 개별 요청 내용·위험도 확인 |
| 기존 묶음에 횟수 갱신, 중복 묶음 생성 방지 | 상담 결과와 경과 관찰/정기 돌봄 검토/종료 결정 |
| 다음 확인 날짜가 되면 검토함에서 우선 표시 | 후속 확인과 이용자·요양보호사 일정 협의 |
| 담당자가 켠 경우 같은 종류의 새 요청을 그 담당자에게 배정 | 개별 위험도 검토와 방문 일정 확정 |

반복 요청 담당 시 최근 7일의 **아직 미배정인 요청만** 함께 맡습니다. 다른 담당자의 요청을 빼앗지 않습니다. 담당자가 결과를 기록하면 그 시점 이후의 요청을 새 요청으로 계산합니다. 검토 이후에도 7일 범위 안에서 새 요청이 3회 쌓이면 다시 ‘개입 검토 필요’로 열립니다. 검토 종료 시 자동 담당 배정은 꺼집니다.

‘정기 돌봄 검토’는 사람이 계획을 세우는 상태이며 반복 방문 일정을 자동 생성하거나 확정하지 않습니다. 긴급 요청을 반복 요청으로 간주해 낮은 위험도로 바꾸거나, 원문을 합쳐 없애거나, 자동으로 해결 처리하지 않습니다. 개별 요청은 계속 보존·검토됩니다.

확인일은 앱 목록을 열거나 새로고침할 때 계산합니다. 문자·푸시·백그라운드 알림은 아닙니다. 업데이트 이전 기록은 **업데이트 전 요청도 찾아 묶기**로 최근 7일을 검사하며, 반복 실행해도 같은 묶음을 중복 생성하지 않습니다.

## 업데이트

1. 서버를 종료하고 기존 `.env`와 `care.db`/PostgreSQL을 백업합니다. 암호화 키를 유지합니다.
2. 최신 소스를 가져온 뒤 backend 폴더에서 기존 가상환경을 활성화합니다.

```bat
.venv\Scripts\activate
python -m pip install -r requirements.txt
python manage.py init-db
```

이 명령은 `booking_coordination`, `visit_records`, `repeat_cases`, `schedule_proposals` 테이블을 추가합니다. 기존 users/care_logs/bookings 컬럼은 바꾸지 않습니다. 기존 DB를 삭제하거나 `setup_env.py`를 다시 실행하지 마세요.

3. 백엔드를 재시작하고 mobile에서 다음을 실행합니다.

```bat
npm ci
npm start -- --clear
```

4. 사회복지사·요양보호사 각각의 계정으로 로그인해 다른 메뉴가 표시되는지 확인합니다. 가상 이용자와 미래 일정으로 배정/변경을 테스트하고, 돌봄 시작은 방문 당일에 확인합니다.

실기기 화면·운영 PostgreSQL 다중 서버 동시성·실제 업무 운영 검증은 별도로 필요합니다. 수행 기록과 반복 요청 상담 내용은 기존 DATA_KEY로 암호화하고, 변경 및 읽기는 감사 기록을 남깁니다.
