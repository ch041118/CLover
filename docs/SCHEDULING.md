# 3단계 일정 조율과 요양보호사 선택

모든 신규 일정은 제안 상태로 전달되고 요양보호사가 수락해야 확정됩니다. 단계는 제안 출처이며, 긴급 요청 때문에 1·2차 처리가 끝날 때까지 기다리도록 강제하지 않습니다.

| 단계 | 담당 | 동작 |
|---|---|---|
| 1차 | 규칙 기반 스케줄러 | 사회복지사가 버튼을 누르면 본인이 검토한 미연결 일반 요청을 접수순으로 최대 100건 처리. 오늘부터 7일 뒤까지 같은 등록 지역의 가장 이른 빈 시간에 제안 |
| 2차 | 사회복지사 | 미연결 일반 요청과 거절된 일정을 확인하고 남은 근무 가능 시간에 제안 |
| 3차 | 사회복지사 | 검토 결과가 긴급인 요청을 가능한 빈 시간에 제안. 이미 확정되거나 수락 대기 중인 다른 일정을 밀어내지 않음 |

스케줄러는 LLM을 사용하지 않으며 주기적으로 자동 실행되는 작업은 아닙니다. 자유서술에 담긴 희망 시간을 자동 해석하지 않으므로 이용자의 시간 요구는 담당자가 확인하고 필요한 경우 변경 제안해야 합니다. GPS 거리·이동 시간·자격·업무량 최적화는 미구현입니다.

## 수락과 거절

- 수락 대기 슬롯도 점유하므로 중복 예약을 차단합니다. 수락 전에는 방문 시작·수행 완료가 불가능합니다.
- 모든 단계에서 요양보호사는 수락하거나 사유를 남겨 거절할 수 있습니다. 수락 후에도 돌봄 시작 전에는 수락을 철회하고 재조율을 요청할 수 있습니다.
- 거절 사유는 암호화 저장되고 일정 관리에 표시됩니다. 해당 근무 슬롯은 마감하며 다시 일할 수 있게 됐다면 요양보호사가 새 슬롯을 등록합니다.
- 거절된 요청을 1차 스케줄러가 반복 제안하지 않습니다. 사회복지사가 기존 일정의 변경 기능으로 새 시간을 제안합니다.
- 시간이나 요양보호사가 바뀌면 새 제안 번호를 발급하고 다시 수락받습니다. 이전 제안을 수락하거나 취소된 제안을 되살릴 수 없습니다.
- 돌봄 시작 후에는 거절 대신 수행 불가·특이사항 보고로 담당자에게 전달합니다.
- 이전 버전에서 이미 확정된 일정은 유지합니다. 새 제안 기록이 없는 기존 일정은 수행 불가 보고 또는 사회복지사 재조율로 처리합니다.
- 제안 이력은 서버에 보존합니다. 요양보호사 화면은 건별 최신 제안을 표시합니다. 푸시·문자는 없으므로 화면을 열거나 새로고침해 확인합니다.

## 업데이트

서버를 종료하고 기존 DB 및 암호화 키를 백업한 후, backend의 기존 가상환경에서 실행합니다.

```bat
python manage.py init-db
```

새 `schedule_proposals` 테이블을 추가하며 기존 데이터를 삭제하지 않습니다. 서버를 재시작하고 mobile에서 `npm start -- --clear`로 앱을 다시 엽니다. 기존 DATA_KEY를 유지해야 합니다.
