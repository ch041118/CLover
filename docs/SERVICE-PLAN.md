# CLover 개편 기획서

**마이크 하나로 요청하고, 일반 일정은 자동 연결하며, 사회복지사는 예외를 조율한다.**

작성일: 2026-09-24 · 개편안 v2 · 개발 기준 제안

이 문서는 9월 24일 개편 요구의 목표와 인수 기준이다. 9월 25일 단일 마이크·대리 등록/기기 연결·저장형 작업 큐·일반 일정 자동 확정·예외 조율·이력/통계 코드를 추가했다. 실제 구현 범위와 실행 방법, 미완료 항목은 [FLOW-V2.md](FLOW-V2.md)를 따른다. 기획 전체가 현장 검증됐다는 뜻은 아니다. 기존 기획은 [보관본](archive/SERVICE-PLAN-2026-09-21.md)에 남긴다.

## 1. 목표와 핵심 결정

목표는 사회복지사가 요청을 읽고 분류하고 요양보호사를 찾아 일정을 전달하는 반복 업무를 줄이는 것이다. 어르신의 조작 수와 사회복지사의 건별 승인 수를 동시에 줄인다.

1. 어르신의 일상 화면에는 큰 마이크 버튼 하나를 중심으로 안내 한 줄만 표시한다. 회원가입, 주소 설정, 분류 선택, 달력 선택을 요구하지 않는다.
2. 마이크를 누르고 말한 뒤 손을 떼면 별도 전송·확인 버튼 없이 접수 절차가 시작된다.
3. 로컬 음성 모델과 LLM이 요청 종류·희망 날짜·시간·제약을 정리하고, 스케줄러가 근무표와 이동 시간을 검증한다.
4. 조건이 명확한 일반 요청은 사회복지사의 사전 검토 없이 자동 배정한다.
5. 요양보호사의 거절·수행 불가, 배정 실패, 해석 불확실 등 예외는 담당 사회복지사에게 넘긴다.
6. 완료된 일반 요청은 별도 승인 없이 기록에 쌓인다. 사회복지사는 전체 처리 이력을 필요할 때 조회한다.

**회원가입 가정:** 사용자의 ‘보호사가 가입한다’는 요구를 요양보호사가 어르신 등록과 초기 기기 설정을 돕는 것으로 해석한다. 가족 보호자 역할은 이번 기본 범위에 추가하지 않는다. 요양보호사의 직원 계정 승인과 담당 사회복지사 연결은 기관 관리자가 한다.

**일정 확정 가정:** 매번 수락을 기다리는 단계는 기본 흐름에서 제외한다. 요양보호사가 사전에 자동 배정에 동의한 근무 시간·지역·업무 범위 안에서만 시스템이 확정할 수 있다. 사전 동의가 없는 근무표는 자동 확정 후보에서 제외한다. 이후에도 요양보호사는 이유를 남겨 수행 불가를 알릴 수 있다.

## 2. 역할과 화면

| 역할 | 주요 업무 | 일상 화면 |
| --- | --- | --- |
| 어르신 | 음성으로 도움 요청·정정·취소 | 큰 마이크 하나, 현재 상태 한 줄, 음성 안내 |
| 요양보호사 | 어르신 등록 보조, 자동 배정 가능 시간·지역 등록, 방문 수행, 예외 사유와 결과 보고 | 오늘 일정, 이용자 등록, 근무 설정, 수행 불가, 완료 보고 |
| 사회복지사 | 담당 팀의 예외 해결, 필요한 일정 직접 조율, 처리 내역 확인 | 개입 필요 목록을 첫 화면으로, 팀 일정과 이력 조회 |
| 관리자 | 직원 승인·담당 관계·운영 기준·API 예산 관리 | 기관 설정과 운영 현황 |

사회복지사 한 명은 여러 요양보호사를 관리한다. 어르신에게도 담당 사회복지사를 명시적으로 연결한다. 처음 등록한 요양보호사 한 명에게 어르신의 모든 방문을 고정하지 않으며, 원칙적으로 같은 담당 팀 안에서 가용한 요양보호사를 찾는다. 타 팀 배정은 사회복지사 조율 대상으로 둔다.

### 초기 설정과 어르신 모드

요양보호사가 직원 계정으로 어르신 등록을 시작하고, 어르신 확인·안내 절차를 거쳐 이름/호칭, 방문 주소, 담당 사회복지사, 필요한 지원과 연락 방법을 등록한다. 음성·로컬 분석·위치 전송 안내도 이때 돕는다. 직원이 임의로 이용자 의사를 대신 확정하는 구조로 만들지 않는다.

어르신 기기에는 일회용 연결 코드나 QR로 어르신 모드만 연결한다. 직원의 로그인 세션을 어르신 기기에 남기지 않는다. 일상 사용에는 ID·비밀번호 재입력을 요구하지 않도록 별도의 갱신 가능한 기기 인증을 설계하고, 분실 시 기관에서 연결을 해제한다. 연결 만료·분실·재연결 관리는 직원 화면에서 수행한다.

직원 설정으로 들어가는 경로는 별도 직원 인증으로 보호한다. 숨겨진 제스처만으로 개인정보나 계정 설정을 열 수 없게 한다. 어르신 화면에 메뉴 탭·로그아웃·가입·좌표·AI 설정을 나열하지 않는다.

## 3. 어르신의 마이크 한 개 사용 흐름

| 상태 | 화면 | 음성·진동 동작 |
| --- | --- | --- |
| 대기 | 큰 마이크, ‘누른 채 말씀하세요’ | 처음 열 때 짧게 사용 안내 |
| 누르는 중 | 같은 마이크가 녹음 상태로 변함 | 짧은 진동 후 녹음 시작 |
| 손을 뗌 | 같은 자리에서 진행 표시, ‘말씀을 접수하고 있어요’ | 전송·저장 진행, 추가 버튼 없음 |
| 서버 접수 완료 | ‘요청을 받았어요’ | ‘요청을 받았습니다. 가능한 일정을 찾고 있어요.’ |
| 일정 확정 | 방문 날짜·시간을 큰 글씨로 표시 | ‘내일 오후 두 시에 요양보호사가 방문합니다.’ |
| 조율 필요 | ‘담당자가 확인하고 있어요’ | ‘일정을 조율하고 있습니다. 정해지면 알려드릴게요.’ |

손을 떼는 것은 **요청 전송 의사**로 처리한다. 방문이 즉시 완료되거나 일정이 무조건 확정된다는 의미는 아니다. ‘접수 완료’, ‘일정 확정’, ‘돌봄 완료’의 안내를 분리한다. 누른 시간이 너무 짧거나 무음이면 요청을 만들지 않고 같은 버튼으로 다시 말하도록 안내한다.

녹음 상한은 우선 30초를 제안한다. 상한에 도달하면 녹음을 멈추고 안내하며, 한 번 누른 동작으로 중복 전송하지 않는다. 화면 이탈·전화 수신 등 운영체제에 의해 녹음이 취소되면 전송 완료로 표시하지 않는다. 기기별 중단 동작은 실기기에서 확인한다.

일반 요청은 별도 ‘접수해 주세요’ 확인 녹음을 없앤다. 다음과 같이 꼭 필요한 경우에만 같은 마이크로 짧게 다시 묻는다.

- 필수 내용이 안 들림: ‘어떤 도움이 필요하신가요?’
- 시간이 모호함: ‘오전 세 시인가요, 오후 세 시인가요?’
- 기존 일정 취소 대상이 여러 개임: ‘내일 방문을 취소할까요?’

정정·취소도 ‘내일 말고 모레로 바꿔줘’, ‘방금 요청 취소해줘’처럼 말한다. 변경 대상을 식별할 수 없으면 임의로 취소하지 않는다. 시간 변경은 후보를 다시 검증한 뒤 확정하고 기존 일정을 원자적으로 해제한다.

장시간 누르기 어려운 이용자를 위해 직원이 동일한 마이크의 조작 방식을 ‘한 번 누르면 시작, 다시 누르면 종료’로 바꿀 수 있게 한다. 기본은 요청한 꾹 누르기 방식이며, 어르신에게 새 메뉴를 추가하지 않는다.

자동 안부 확인은 주 화면에서 설정 카드를 제거하고 별도 선택 기능으로 둔다. 도움 요청 녹음·접수 중에는 먼저 말을 걸거나 녹음을 시작하지 않게 한다.

## 4. 날짜·시간 해석 정책

시간 기준은 한국 시간이며, ‘내일’은 **최초 발화 접수 시각** 기준으로 해석한다. 대기열 처리가 자정을 넘겨도 의미가 바뀌면 안 된다. LLM은 원문에 등장한 근거와 해석값을 함께 반환한다.

| 발화 예시 | 기본 처리 |
| --- | --- |
| ‘내일 오후 두 시에 병원 같이 가줘’ | 내일 14시 조건. 병원 도착 시각인지 방문 시작 시각인지 불명확하면 한 번 질문 |
| ‘내일 오전에 청소 좀 해줘’ | 기관에서 정한 오전 시간 범위 안에서 가장 이른 가능한 방문 |
| ‘오늘 중으로 장 좀 봐줘’ | 오늘 근무 가능 시간 안에서 가장 이른 방문. 오늘이 안 되면 조율 필요 |
| ‘밥 준비 좀 도와줘’ | 별도 날짜·시간 제약 없음 → 가장 빠른 가능한 일정 탐색 |
| ‘가능한 빨리 와줘’ | 일반 요청의 우선 시각을 가능한 빠르게 탐색. 이 말만으로 긴급 요청으로 단정하지 않음 |
| ‘내일 두 시, 안 되면 세 시도 돼’ | 명시한 두 후보만 순서대로 검토 |
| ‘지난 화요일에 와줘’ 또는 모순된 날짜 | 날짜 확인 필요. 임의로 다음 주로 바꾸지 않음 |

**구분해야 할 두 경우:** 시간을 말하지 않은 요청은 가능한 빨리 배정한다. 시간을 명시했는데 그 시간에 빈 사람이 없는 요청은 다른 시간으로 몰래 바꾸지 않는다. 발화 또는 초기 설정에서 허용한 대체 범위 안에서만 변경하며, 범위를 벗어나면 사회복지사가 조율한다.

‘오전/오후’ 범위, 기본 탐색 기간, 업무별 방문 길이와 이동 여유분은 기관 설정값이다. 초기 제안은 오전 09~12시, 오후 12~18시, 탐색 기간 7일이며 운영 전 확정한다. 복약 등 시각 준수가 필요한 요청은 일반적인 시간 생략 규칙만으로 처리하지 않는다.

## 5. 자동 배정 방식

### 단계별 처리

1. **접수 저장:** 고유 접수번호와 중복 방지 키를 저장한다. 모델 추론이 끝날 때까지 앱 화면을 막아 두지 않는다.
2. **내용 구조화:** 로컬 음성 모델로 글을 만들고 로컬 LLM으로 도움 종류·희망 시간·업무 조건을 추출한다. 모델의 자기평가 신뢰도 숫자만으로 자동 확정을 결정하지 않는다.
3. **자동 처리 가능 여부 판정:** 기관이 허용한 일반 업무인지, 시간·주소·담당 관계가 준비되었는지, 해석 충돌이 없는지 검사한다. 긴급·지원 범위 밖·불확실 요청은 담당자에게 넘긴다.
4. **후보 축소:** 담당 팀, 업무 수행 가능 범위, 활동 지역, 자동 배정 동의, 근무 시간, 이미 잡힌 일정과 휴게 시간을 DB에서 먼저 검사한다.
5. **이동 시간 검증:** 앞 방문 또는 출발지 → 새 방문 → 다음 방문에 실제로 들어갈 수 있는지 확인한다. 사전 필터를 통과한 상위 후보만 네이버 Directions로 조회한다.
6. **후보 선택:** 시간 제약 준수 → 가장 이른 도착 → 짧은 이동 시간 → 업무량 균형 → 동률 고정 기준 순으로 결정한다. LLM이 데이터베이스의 일정을 직접 확정하지 않는다.
7. **최종 확정:** 일정 잠금 후 겹침·최신 근무표·조건을 다시 확인하고, 방문과 자동 배정 이력·알림 작업을 함께 저장한다.
8. **통지와 수행:** 어르신에게 날짜·시간을 알려주고 요양보호사 일정에 반영한다. 이후 방문 시작·완료·특이사항을 기록한다.

‘근처’는 고정된 주소와 방문 동선에 따른 이동 가능성을 뜻한다. 실시간 GPS 추적을 전제로 하지 않는다. 구가 같다는 이유만으로 가까운 사람이라 판단하지 않으며, 먼 후보를 모두 외부 API로 조회하지도 않는다.

근무 가능 시간은 큰 블록으로 등록할 수 있고, 필요한 방문 길이와 이동 시간만큼 나누어 사용한다. 예를 들어 09~12시 근무 블록에 30분 요청 하나가 들어왔다고 3시간 전체를 예약하지 않는다. 다음 방문까지의 시간도 함께 확보한다.

### 호출량과 비용

주소 검색은 초기 등록·주소 변경 시에 수행한다. 일정 후보 탐색 때 같은 주소를 매번 다시 검색하지 않는 구조를 검토하되, 제공자 결과를 별도 저장·재사용하는 조건은 실제 계약 범위를 따라야 한다. 기존 캐시 기능의 기본 비활성 설정은 유지한다.

일반 후보는 먼저 DB에서 축소하고, 상위 3명부터 이동 시간을 확인하는 방식을 초기값으로 제안한다. 후보가 탈락하면 정해진 작업별 호출 예산 안에서만 다음 후보로 확장한다. API 오류·한도 도달은 ‘이동 가능’이나 ‘배정할 사람이 없음’과 구분한다. 실패 원인을 기록해 사회복지사가 불필요하게 사람에게 연락하지 않게 한다.

## 6. 요양보호사의 예외와 사회복지사의 개입

요양보호사는 자동 배정된 일반 일정에 매번 수락 버튼을 누를 필요가 없다. 단, 근무 가능 시간과 자동 배정 범위를 사전에 명시적으로 등록해야 한다. 당일 갑작스러운 사정이 생기면 ‘수행 불가’를 선택하고 이유를 입력한다.

사유는 시간 충돌, 건강·개인 사정, 이동 곤란, 업무 범위 불일치, 이용자 변경 요청, 기타로 분류하고 필요한 설명을 붙인다. 이유는 사회복지사에게 제공하고 어르신에게는 필요한 일정 변경 안내만 전달한다.

| 개입 사유 | 자동 처리 | 사회복지사가 할 일 |
| --- | --- | --- |
| 요양보호사 거절·확정 후 수행 불가 | 배정 차질 표시, 담당자 알림, 대안 후보 계산 | 사유 확인 후 사람·시간 직접 변경 |
| 지정 시간에 후보 없음 | 탐색 범위와 탈락 이유 요약 | 어르신과 가능한 대체 시간 조율 |
| 음성·날짜 해석 불확실 | 짧은 재질문 1회, 여전히 불명확하면 전달 | 필요한 내용만 확인 |
| 반복되는 미해결 요청 | 같은 문제의 이력 묶음과 이전 조치 표시 | 정기 지원이나 다른 조치 검토 |
| 긴급·지원 범위 밖 | 일반 배정 대기열에서 분리, 즉시 안내·알림 | 기관의 대응 절차에 따라 판단 |
| 지도·모델·알림 장애 | 제한된 자동 재시도와 기술 오류 표시 | 장기 지연·방문 임박 건만 우선 조율, 기술 담당은 장애 처리 |
| 미방문·특이사항 | 시간·보고 기준으로 예외 생성 | 실제 수행 여부와 후속 조치 확인 |

요양보호사가 한 번 거절한 요청을 자동으로 같은 사람에게 다시 보내지 않는다. 사용자 요구대로 거절 이후에는 담당 사회복지사가 조율의 책임을 맡으며, 시스템은 대안 준비만 돕는다. 거절된 요청 때문에 해당 요양보호사의 근무 블록 전체를 무조건 닫지 않는다. 그 요청만 못 하는지, 해당 시간에 아예 일할 수 없는지 구분한다.

기존 1차·2차·3차의 순차 실행 버튼 대신, **일반 요청은 즉시 자동 처리 / 예외는 사회복지사 조율 / 긴급은 별도 우선 대응**으로 전환한다. 긴급 처리 때문에 이미 확정된 다른 일정을 자동으로 밀어내지 않는다.

## 7. 알림·처리 이력과 업무 경감 확인

자동 배정에는 앱을 보고 있지 않아도 도착하는 요양보호사 알림이 필요하다. 현재의 새로고침 방식만으로는 자동 운영할 수 없다. 배정·수행 불가·재조율·변경 확정·방문 임박을 알림 작업으로 기록하고 재시도와 전달 결과를 관리한다. 푸시 도착이 실제 읽음을 뜻하지 않으므로 알림 미확인과 임박 일정의 개입 기준을 별도로 둔다.

어르신에게는 앱 전면에서 음성으로 안내하고, 화면이 잠겨 있거나 앱이 종료된 경우 알림으로 도착 사실을 알려 앱을 열면 읽어준다. 백그라운드에서 항상 스피커로 읽어줄 수 있다고 전제하지 않는다.

사회복지사의 첫 화면에는 개입이 필요한 항목만 우선 보여준다. 일반 완료 건은 건별 확인·승인을 요구하지 않고 내역에서 조회한다.

**한 요청의 이력:** 접수 시각 → 원문과 구조화 결과 → 자동/수동 처리 판단 근거 → 후보 탈락 사유 → 배정 대상·시간 → 알림 상태 → 거절 이유 → 담당자의 조율 → 방문 시작 → 완료/미수행 보고. 수정 전·후 값과 처리 주체를 보존하고, 요양보호사에게는 수행에 필요한 정보만 제공한다.

| 지표 | 정의 |
| --- | --- |
| 사람 개입 없는 완료율 | 사회복지사의 업무 조치 없이 방문 완료된 요청 / 전체 접수 요청. 조회만 한 것은 개입으로 계산하지 않음 |
| 사회복지사 건당 조치 수 | 실제 분류 수정·연락·재배정·후속 조치 횟수 / 접수 건수 |
| 개입 사유별 건수 | 거절, 후보 없음, 시간 불명확, 긴급, 시스템 장애 등 |
| 처리 속도 | 손을 뗀 뒤 서버 접수 확인, 접수 후 일정 확정까지의 중앙값과 상위 95% 시간 |
| 일정 품질 | 확정 후 변경률, 거절률, 미방문률, 재조율 소요 시간 |
| 요청 분포 | 도움 종류별 전체/자동 처리/개입/완료/취소 건수 |
| 지도 사용량 | 실제 호출 시도·허용된 재사용·한도 중단 건수 |

초기 목표값은 검증 전 목표로, 손을 뗀 뒤 1초 내 기기 반응, 정상 개발망에서 접수 저장 응답 3초 이내, 일반 요청 배정 30초 이내를 제안한다. 실제 PC에서 측정하여 수정한다. 업무시간 절감률은 기준 운영과 비교 측정하기 전에는 수치로 주장하지 않는다.

## 8. 현재 코드와 달라져야 할 부분

| 현재 구현과 근거 | 새 기획과 맞지 않는 점 | 변경 계획 |
| --- | --- | --- |
| `mobile/App.tsx`: 어르신용 5개 탭·로그아웃·설정 | 선택과 탐색이 많음 | 어르신 전용 마이크 화면과 직원 화면 분리 |
| `VoiceRequest.tsx`: 25초 녹음 후 별도 확인 녹음 7초 | 손을 떼어도 자동 접수되지 않음 | 누름 시작/해제 종료 방식, 확인 녹음 제거, 중복 방지 |
| `main.py` 회원가입과 `Auth` 화면 | 어르신의 가입·로그인을 요구 | 직원 보조 등록, 담당 관계, 어르신 기기 연결·갱신 인증 신설 |
| `main.py` 접수 시 동기 분류 후 저장 | 모델이 느리면 접수도 대기 | 먼저 접수 저장, 내구성 있는 처리 대기열에서 분석·배정 |
| `speech.py`: 요청마다 음성 모델 프로세스 로드 | 짧은 대화에도 초기 로딩 지연 | 기관 PC 자원 측정 후 상주 음성 작업자 검토, 작업 제한·복구 유지 |
| `coordination.py`: `review_required`인 요청 배정 금지 | 모든 요청에 사회복지사 개입 필요 | 자동 처리 정책과 예외 판정 분리. 단순히 검토 플래그를 무조건 해제하지 않음 |
| `/api/worker/scheduler/run`: 담당자 버튼·검토 완료 건만 처리 | 접수 즉시 자동 연결 안 됨 | 접수 처리 완료 이벤트로 스케줄러 실행, 기존 버튼은 예외 재평가용 |
| 날짜·시간 발화 해석 없음 | 원하는 시간 반영 불가 | 구조화 시간 범위·원문 근거·유연성 추출과 검증 추가 |
| `Availability`와 슬롯 예약 | 요청 길이에 비해 근무 블록 전체 점유 가능 | 방문별 시작·종료와 블록 내 빈 구간 계산 |
| 매 제안마다 `accept` 필요 | 정상 건에도 응답 대기가 생김 | 사전 동의한 범위의 자동 확정, 수동 조율 변경 시 별도 확인 정책 |
| 거절 시 슬롯 `closed` 처리 | 한 요청 거절로 근무 시간 전체가 사라짐 | 요청별 거절과 실제 근무 불가를 분리 |
| `CaregiverTeam`과 이력 조회 | 재사용 가능한 역할 구조 | 유지하고 어르신 담당 사회복지사 관계 추가 |
| 지도 검증·호출 예산·기록 | 활용 가능하지만 후보 축소 부족 | DB 우선 필터, 상위 후보 조회, 지도 오류와 인력 부족 구분 |
| 자동 안부 확인 카드 | 마이크 중심 화면을 복잡하게 함 | 초기 직원 설정으로 이동, 요청 녹음과 충돌 방지 |
| 수동 새로고침 중심 | 자동 배정을 놓칠 수 있음 | 푸시 알림, 전달 결과, 임박·미확인 예외 처리 |
| `OperationHistory` | 조회 기능은 있으나 모든 변경 사유를 한눈에 보기 어려움 | 요청 단위 통합 타임라인과 자동/수동 구분 |

기존 동시 예약 방지, 역할 권한, 암호화, 담당 팀, 수행 보고, 지도 API 예산은 유지·확장한다. 모든 일반 요청의 사전 승인과 어르신의 수동 일정 선택은 기본 경로에서 제거한다. 안내문 초안 등 부가 기능은 직원 보조 메뉴로 내리고 이번 핵심 개발 순위에서 제외한다.

## 9. 개발 설계 기준

다음은 제안이며 신규 API·테이블은 아직 구현하지 않았다.

- **등록/기기:** 어르신 프로필·담당 사회복지사·등록 직원, 기기 연결 토큰과 철회 기록, 직원의 대리 등록 감사 이력.
- **접수:** 중복 방지 키, 최초 발화 시각, 음성 처리 상태, 요청 원문, 종류, 시간 범위, 시간 유연성, 원문 근거, 자동 처리 정책 버전.
- **일정:** 근무 블록과 방문 구간 분리, 이동 여유분, 자동 배정 허용 범위, 배정 버전, 확정 시점과 처리 주체.
- **예외:** 개입 사유 코드, 담당자, 처리 기한, 조율 내용, 해소 시각. 예외가 생겼다고 원래 요청을 삭제하지 않음.
- **이벤트/알림:** 요청과 연결된 상태 변경 이력, 알림 전송·재시도·열람 상태. 일정 확정과 알림 생성은 함께 저장.
- **작업 대기열:** DB에 작업을 먼저 남기고 별도 작업자가 처리. 재시작 복구, 제한된 재시도, 중복 실행 방지. 단순한 요청 후 메모리 작업만으로 운영하지 않음.

잠깐의 무음·전송 실패를 접수 성공으로 읽어주지 않는다. 서버 응답을 못 받았을 때는 동일 접수 키로 저장 여부를 확인하고, 새 요청을 무조건 다시 만들지 않는다. 음성 원음은 처리 중에만 암호화·접근 제한하여 임시 보관하고, 처리가 끝나면 삭제하는 보존 정책을 명시한다. 기존에는 처리 후 파일을 정리하므로 비동기 대기열 도입 시 임시 보관 방식도 함께 바꿔야 한다.

예시 상태는 ‘접수됨 → 해석 중 → 배정 탐색 → 확정 → 방문 중 → 완료’다. 각 단계에서 ‘개입 필요’로 분기할 수 있고, 조율 후에는 다시 ‘확정’으로 돌아간다. ‘개입 필요’와 ‘취소’, ‘수행 불가’, ‘완료’를 하나의 종료 상태로 합치지 않는다.

## 10. 개발 순서와 완료 조건

| 순서 | 구현 묶음 | 완료 확인 |
| --- | --- | --- |
| 1 | 직원 보조 등록·기기 연결·마이크 화면 | 어르신이 가입/로그인/분류/달력 화면 없이 요청 가능 |
| 2 | 누름 녹음·해제 전송·비동기 접수·시간 해석 | 저장 확인 안내, 중복 접수 방지, 모델 장애에도 접수 이력 유지 |
| 3 | 자동 배정 동의·빈 구간 계산·이동 검증·확정 | 일반 요청이 사회복지사 클릭 없이 가능한 일정으로 연결 |
| 4 | 배정 알림·거절 사유·예외 업무함·직접 재조율 | 요양보호사 수행 불가가 담당자에게 전달되고 대체 일정 확정 |
| 5 | 수행 결과·통합 이력·분류별 통계 | 사회복지사가 자동 완료와 개입 결과를 조회 가능 |
| 6 | 실기기·실모델·현장 시범 검증 | 사용성·처리 시간·오배정·실제 업무량을 측정 |

1~5단계를 함께 마친 범위를 첫 시범 운영판으로 본다. 자동 배정만 넣고 알림·거절·재조율을 뒤로 미루지 않는다. 기간·인력·예산은 아직 산정하지 않았다.

### 필수 인수 시나리오

1. ‘식사 준비 도와줘’ → 손을 떼면 한 건만 접수되고 가장 빠른 가능한 일반 일정으로 자동 확정.
2. ‘내일 오후 두 시’ → 해당 시각을 지키거나 개입 필요로 분기. 임의로 오늘 방문을 확정하지 않음.
3. 같은 요청의 전송 재시도·작업자 재시작 → 중복 방문 생성 없음.
4. 두 어르신이 같은 빈 시간에 요청 → 한 요양보호사에게 겹치는 일정 확정 없음.
5. 가까워 보여도 앞뒤 이동 시간이 부족한 후보 → 자동 확정 제외.
6. 요양보호사 사전 동의 밖의 시간·지역·업무 → 자동 배정 제외.
7. 요양보호사 수행 불가 → 사유와 대안이 담당 사회복지사에게 전달되고 같은 사람에게 반복 자동 배정하지 않음.
8. 사회복지사 재조율 → 변경 이력과 새 알림이 남고 이전 일정으로 방문 시작 불가.
9. 일반 방문 완료 → 사회복지사의 추가 승인 없이 실적으로 집계.
10. 모델·지도·알림 실패 → 실패 원인이 구분되고 오래된 결과로 배정 성공 처리하지 않음.
11. 앱 잠금·재실행·기기 분실 → 녹음 자원이 정리되고 직원 권한이 노출되지 않음.
12. 무음·매우 짧은 누름·사투리·취소 발화 → 허위 접수나 엉뚱한 일정 취소 방지.
13. 손 힘이 약한 이용자 → 직원이 설정한 대체 조작으로 같은 한 개 버튼 사용 가능.
14. 반복되는 미해결 요청 → 단순 중복 삭제 대신 사회복지사의 확인 지점 생성.
