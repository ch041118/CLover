# CLover 서비스 기획서

생활 도움 접수부터 일정 조율과 직접 돌봄까지

기준일 2026년 9월 20일 · 현재 구현 기준 · 기관 운영 및 개발 검토용

## 1 서비스 목적

CLover의 우선 목표는 사회복지사가 직접 수행하던 접수 정리·분류·전달 준비의 일부를 AI가 먼저 처리해 검토 업무를 줄이는 것이다. 어르신의 생활 속 도움 요청을 글이나 음성으로 접수하고, 사회복지사가 요청을 검토하여 요양보호사와 연결하는 모바일 서비스다. 사회복지사는 일정과 후속 조치를 관리하고, 요양보호사는 제안받은 일정을 선택한 뒤 직접 돌봄을 수행한다.

접수 화면은 식사 준비, 산책과 외출 동행, 가벼운 집안일처럼 부담 없이 요청할 수 있는 일상 활동을 중심으로 구성한다. 긴급 상황도 구분하지만 서비스 전체를 위험 여부 확인이나 안부 확인에만 맞추지 않는다.

### 역할과 결정 권한

| 역할 | 주요 기능 | 본인이 결정하는 사항 |
| --- | --- | --- |
| 어르신 | 글·음성 접수, 지역과 일정 신청, 내 기록 확인 | AI 사용 여부, 도움받을 지역, 접수와 취소 |
| 사회복지사 | 요청 검토, 일정 제안·변경, 통계와 반복 요청 관리 | 분류 검토 결과, 제안할 일정, 상담·후속 조치 |
| 요양보호사 | 근무 가능 시간 등록, 직접 돌봄과 수행 보고 | 활동 지역과 시간, 일정 수락·거절 |
| 관리자 | 회원 승인과 감사 기록 확인 | 이용 계정의 승인·관리 |

### 현재 제품 범위

Android·iPhone 앱과 기관 PC의 서버로 구성한 단일 기관용 구현이다. 아래의 구현 완료 표시는 코드와 자동 검사 기준이며, 운영 배포 완료나 실제 어르신을 대상으로 한 사용성 검증을 뜻하지 않는다. 이 문서는 개발된 기능, 이번에 추가한 일정 정책, 후속 개발 항목을 함께 정리한다.

## AI 업무함 개정 사항

접수 시 로컬 AI가 분류·요약·원문 근거를 함께 준비한다. 사회복지사는 AI 업무함에서 일반 요청을 확인 후 묶음 승인하고, 긴급·불확실·반복 요청은 개별 확인한다. 원문 발췌를 바탕으로 전달문을 준비하며 사회복지사가 검토한 내용만 연결된 요양보호사에게 공개한다. 그대로 승인·수정·묶음 승인 건수를 기록하되 시간 절감률은 아직 측정하지 않았다. 세부 조건과 한계는 [업무 경감 개선안](AI-WORKFLOW-IMPROVEMENTS.md)을 따른다. 이전 Word 기획서는 9월 19일 기준이며 이번 변경은 이 원문에 반영했다.

## 2 어르신 접수와 AI 이용

### 가벼운 생활 도움 접수

도움 종류는 식사, 이동, 집안일, 말벗, 복약, 기타로 구분한다. 일상적인 선택 항목을 먼저 제시하고 긴급 항목은 별도로 펼쳐 선택한다. 어르신은 글과 선택 항목으로 필요한 도움을 설명하고 내 요청 화면에서 접수 결과를 확인한다.

### 타이핑 없는 음성 접수

말하기 버튼을 누르고 필요한 도움을 이야기하면 기관 PC가 음성을 글로 바꾼다. 앱은 변환된 내용을 보여주며, 어르신이 확인 버튼을 누르고 “접수해 주세요”라고 말해야 요청이 접수된다. “취소해 주세요” 또는 불명확한 응답은 접수하지 않는다.

본문 녹음은 25초, 확인 녹음은 7초 후 자동 종료한다. 화면을 벗어나거나 앱이 배경으로 이동하면 녹음을 중단한다. 현재는 녹음 시작과 확인에 버튼 조작이 필요하며, 호출어로 시작하는 상시 대화와 음성 읽어주기는 포함하지 않는다.

### AI는 한 번 설정하고 접수마다 적용

첫 로그인에서 로컬 AI 분석 안내를 보여주고 사용 여부를 한 번 저장한다. 다음 접수부터 저장된 설정을 적용하여 매번 별도로 AI를 선택하는 부담을 줄인다. 설정에서 철회할 수 있으며, 동의하지 않아도 요청은 접수되고 담당자가 확인한다.

| 처리 | 현재 방식 | 사람의 확인 |
| --- | --- | --- |
| 음성 변환 | 기관 PC의 faster-whisper tiny 모델 | 인식 문장을 확인한 뒤 접수 |
| 요청 분류 | 긴급 규칙 우선 확인 후 동의에 따라 로컬 Qwen 모델 사용 | 사회복지사가 모든 분류 검토 |
| 안내문 초안 | 주제별 로컬 AI 생성, 실패하면 기본 문구 제공 | 담당자가 편집·검토 후 사용 |

AI를 사용할 수 없거나 출력이 잘못된 경우 외부 AI로 전환하지 않는다. 요청은 담당자 확인 대상으로 남기고, 안내문 화면에서는 AI 작성과 기본 문구 대체를 구분한다. 실제 소음·사투리·작은 목소리에서의 인식률은 별도 검증이 필요하다.

## 3 지역 연결과 3단계 일정 운영

### 지역과 근무 가능 시간

어르신은 도움받을 지역을, 요양보호사는 일할 지역과 날짜·시작·종료 시간을 등록한다. 같은 시·도와 시·군·구에 속하는 일정으로 연결한다. 어르신의 직접 검색은 희망 시간 범위 안에 전체가 들어오는 근무 슬롯을 대상으로 한다. 시간 기준은 한국 시간이며 미래 90일까지 등록한다.

| 단계 | 처리 주체 | 제안 방식 |
| --- | --- | --- |
| 1차 자동 제안 | 규칙 기반 스케줄러 | 담당자가 실행하면 검토한 미연결 일반 요청을 접수순으로 처리하고 같은 지역의 가장 이른 빈 시간에 제안 |
| 2차 남은 시간 조율 | 사회복지사 | 미연결 일반 요청과 거절된 일정을 살펴 남은 근무 가능 시간에 직접 제안 |
| 3차 긴급 일정 | 사회복지사 | 긴급으로 검토한 요청을 빈 시간에 제안하며 기존 수락 대기·확정 일정을 덮어쓰지 않음 |

1차 실행은 오늘부터 7일 뒤까지의 슬롯과 최대 100개 요청을 대상으로 한다. 현재는 버튼 실행 방식이다. 긴급 요청은 자동 제안에서 제외해 직접 조율 대상으로 표시하며, 1·2차 종료를 기다리도록 강제하지 않는다. 이용자가 글로 쓴 희망 시간은 자동 해석하지 않으므로 담당자가 확인해야 한다.

### 수락과 거절 흐름

제안 → 요양보호사 수락 대기 → 수락 시 확정 → 방문 당일 돌봄 시작 → 수행 보고 순서다. 어느 단계의 제안이든 요양보호사가 거절할 수 있고, 수락한 뒤에도 돌봄 시작 전에는 사유를 남겨 재조율을 요청할 수 있다.

거절하면 사회복지사 화면에 재조율 필요와 사유가 표시된다. 거절된 슬롯은 마감하고 같은 요청을 자동으로 반복 제안하지 않는다. 사회복지사는 기존 일정에서 다른 시간이나 요양보호사를 선택해 새로 제안한다. 변경된 일정은 다시 수락해야 하며 이전 제안 번호로 수락할 수 없다.

수락 대기 중인 시간도 중복 예약을 차단한다. 시작 이후에는 거절 대신 수행 불가·특이사항을 보고한다. GPS 거리, 이동 소요 시간, 슬롯 부분 분할과 정기 방문 자동 생성은 아직 지원하지 않는다.

## 4 사회복지사의 관리와 사람의 개입

### 요청 검토와 직접 돌봄의 연결

사회복지사는 새 요청을 담당하고 원문·선택 항목·분류를 검토한다. 검토하지 않은 요청은 요청 기반 일정 제안에 연결할 수 없다. 다른 사회복지사가 담당한 일정을 임의로 변경할 수 없고, 어르신이 직접 신청한 일정은 관리 담당을 맡은 뒤 제안한다.

요양보호사는 확정된 일정을 방문 당일 시작하고 수행 내용을 남긴다. 완료는 시작 후에만 가능하다. 수행 불가나 특이사항은 사회복지사 확인 필요 상태로 남아 담당자의 연락과 후속 조율로 이어진다. 상담 원문 전체 대신 연결된 이용자 ID, 지역, 시간, 도움 종류를 제공한다.

### 분류별 현황과 통계

| 집계 항목 | 표시 내용 |
| --- | --- |
| 요청 수 | 전체와 식사·이동·집안일·말벗·복약·기타별 건수 |
| 분류와 검토 | 종류별 현재 위험도, 분류 검토 대기·완료, 담당 미배정·배정 |
| 일정 수 | 조율·수락 대기, 확정, 거절, 진행, 완료, 특이사항, 취소 상태별 건수 |
| 기간 | 최근 7일·30일·90일, 접수 시각 기준 전체 집계 |

통계는 단일 기관 전체 기준이며 목록의 100건 표시 제한과 별개다. 요청 검토 완료와 돌봄 완료를 구분한다. 방문일 기준 실적이나 과거 시점의 위험도 변경 추이는 현재 통계에 포함하지 않는다.

### 반복 요청의 자동 묶음과 개입

같은 어르신이 같은 도움 종류로 최근 7일에 3회 이상 요청하면 반복 검토 건을 만든다. 문장이 같다는 의미가 아니라 같은 종류의 도움이 반복된다는 신호다. 원문을 합쳐 없애거나 반복만을 이유로 해결 처리하지 않는다.

사회복지사가 묶음을 맡고 개별 내용을 확인한 후 경과 확인, 정기 돌봄 검토, 검토 종료를 선택한다. 상담·조치 내용과 다음 확인 날짜를 기록하며, 필요하면 같은 종류의 새 요청을 자신에게 자동 배정하도록 설정한다. 새 요청의 위험도 검토와 방문 제안·수락은 계속 별도로 진행한다.

검토 이후에도 7일 내 새 요청이 3회 쌓이면 다시 개입 검토 대상으로 표시한다. 확인일이 된 건은 목록에서 우선 보여준다. 현재는 목록 조회·새로고침 기준이며 문자·푸시 알림은 없다.

## 5 시스템 구성과 운영 조건

### 모바일 앱과 기관 서버

모바일 앱은 Expo와 React Native로 구성한다. Python FastAPI 서버가 로그인, 접수, 일정, 통계와 권한을 처리하고 데이터베이스에 기록한다. SQLite 개발 환경을 제공하며 PostgreSQL 구성을 지원한다. 텍스트 AI와 음성 변환은 기관 PC에서 실행하도록 구성한다.

텍스트 AI는 Ollama의 qwen2.5:0.5b, 음성은 별도 설치하는 faster-whisper tiny 모델을 사용한다. 모델 다운로드는 설치 단계에 필요하다. 요청 처리 때 외부 모델로 전환하지 않으며, 저사양 PC의 실제 처리 시간과 메모리 사용량은 측정이 필요하다.

### 데이터 접근과 보존

| 대상 | 현재 처리 |
| --- | --- |
| 회원과 권한 | 가입 후 관리자 승인, 역할과 담당자에 따른 API 접근 제어 |
| 민감한 내용 | 요청 원문, 수행 기록, 반복 요청 조치, 거절 사유를 암호화 저장 |
| 음성 파일 | 앱 캐시와 서버 처리용으로 사용 후 정리하며 요청 원음 장기 보관 기능은 없음 |
| 일정 이력 | 제안 번호·단계·수락·거절 기록 보존, 주요 변경 감사 기록 |
| 정보 공유 | 요양보호사에게 상담 원문 전체를 제공하지 않음 |

### 설치와 이번 업데이트

서버 소스를 업데이트하기 전 기존 데이터베이스와 환경 설정·암호화 키를 백업한다. backend 가상환경에서 python manage.py init-db를 실행하면 이번 일정 제안 테이블이 추가된다. 기존 데이터를 삭제하거나 암호화 키를 새로 만들지 않는다. 서버와 앱 개발 서버를 재시작한다.

이전 버전에서 이미 확정한 일정은 유지한다. 제안 이력이 없는 기존 일정은 수행 불가 보고 또는 사회복지사의 재조율로 처리한다. 상세 실행 순서는 저장소의 README, docs/MOBILE.md, docs/SCHEDULING.md에 정리한다.

### 현장 운영 전에 정할 사항

기관은 상세 방문 장소와 현장 지시 전달, 요양보호사 자격 확인, 비용 처리 절차를 정해야 한다. 운영 환경의 HTTPS, 계정·장비 접근 통제와 백업도 필요하다. 긴급 분류는 담당자가 확인할 신호이며 자동 신고나 응급 출동 시스템은 포함하지 않는다.

### 검증 결과와 한계

AI 업무함 추가 후 서버 테스트 103개, 앱 테스트 11개와 TypeScript 검사가 통과했다. 묶음 승인 조건과 원자적 저장, 검토 중 상태 변경, 원문 근거 검증, 역할별 접근과 암호화 저장을 확인했다. 자동 검사는 실제 모델 품질과 현장 업무시간 감소를 검증하지 않는다.

실기기 마이크와 화면, 실제 Ollama·음성 모델의 추론 성능, 운영 PostgreSQL 다중 서버 동시성은 이 결과에 포함되지 않는다. 빌드 성공이나 코드 테스트 통과를 현장 운영 검증 완료로 해석하지 않는다.

### 후속 개발 제안

우선 가상 이용자와 각 역할 계정으로 접수부터 방문 보고까지 검증하고, 어르신이 버튼과 음성 확인 절차를 이해하는지 관찰한다. 이어 제안·거절·긴급 요청 알림과 응답 기한을 추가해 새로고침에 의존하는 운영을 개선한다.

다음으로 이용자 희망 시간의 구조화 입력, 요양보호사 업무량과 이동 시간, 반복 방문을 일정 조율에 반영한다. 여러 기관으로 확대할 때는 기관별 데이터 격리와 보호자 대리 관계를 먼저 설계한다. 위 순서는 제안이며 확정된 일정·예산은 아니다.

### 시범 운영에서 기록할 지표

접수 완료율과 음성 재시도 횟수, 접수부터 첫 제안까지의 시간, 제안 수락률과 거절 사유, 재조율 소요 시간, 방문 완료율, 반복 요청 검토 소요 시간을 기록한다. 현재 자동 수집·대시보드가 모두 구현된 지표는 아니며 시범 운영 후 목표값을 정한다.

### 작성 근거

현재 저장소의 README와 역할·자동화·음성·일정 안내, backend/app의 접수·매칭·조율 코드, mobile/src/components의 역할별 화면, 자동 테스트 결과를 기준으로 작성했다. 구현 범위가 바뀌면 이 문서와 저장소의 서비스 기획서를 함께 갱신한다.
